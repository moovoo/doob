# doob

Modular desktop audio player. Currently: a Qt Widgets layout editor with composable
widgets (Splitter, Tabs) inside recursive WidgetContainers, an edit mode, a
SQLite database for library/playlist content, a central settings manager
(`SettingsManager`, settings.json — user settings and session state alike),
per-name layout and style files (the `layouts/` and `styles/` dirs,
with read-only presets — see `docs/persistence.md`), and a `.so` plugin
system (source providers, widgets and playback drivers — see
`docs/plugins.md`).

## Build

```
cmake -S . -B build
cmake --build build
```

## Test

```
ctest --test-dir build --output-on-failure
```

Tests are QTest executables in `tests/` (one `QTEST_MAIN` class per file), registered
with CTest and run headless via `QT_QPA_PLATFORM=offscreen`. The gallery
screenshot test is the exception: it writes PNGs into the repo's `gallery/`
(committed artifacts, font rendering is machine-dependent), so it is not part
of the default gate — build it with `-DDOOB_BUILD_GALLERY_TEST=ON` when you
want fresh shots. Production code lives in
the `doob_lib` shared library so tests and the `doob` app share it (shared, not
static: a plugin's .so links against it, so a loaded plugin and the host process
share one copy of the singletons). **Plugins are
self-sufficient about testing**: a plugin's tests live in `plugins/<plugin>/tests/`
and are built and registered with CTest by the plugin's own CMakeLists (the
root's `enable_testing()` precedes the `add_subdirectory(plugins/...)` calls), so a
standalone plugin build (`cmake -S plugins/<plugin>` against the installed API)
builds and runs the plugin's tests too.

## Packaging (AppImage)

`packaging/appimage/build.sh` builds the distributable AppImage — the
ffmpeg and Spotify plugins fully bundled, everything the image links
against inside it — in a pinned `fedora:42` build image
(`packaging/appimage/Dockerfile`, digest-pinned; the distro's Qt 6.10.2,
chosen because Spotify playback needs a WebEngine with AAC-MSE, which
the aqt-built Qt does not have). The flow: compile, test (the default
gate), assemble the AppDir, bundle the ldd closure
(`bundle-deps.sh`), audit that every ELF resolves from inside, package
with appimagetool. The artifact is bit-for-bit reproducible for the
same source + image digest; three things make that true:
`SOURCE_DATE_EPOCH` is pinned (it stamps the resources rcc embeds
from the freshly copied SDK), the AppDir's mtimes are normalized to a
constant, and appimagetool's bundled mksquashfs 4.4 is pinned to
`-processors 1` — its multithreaded pack is not deterministic (thread
scheduling changes individual blocks' compressed sizes, shifting every
later offset; ~20 MB of the ~218 MB payload differs between runs). `--sign KEYID` adds the embedded GPG signature
plus a detached `.asc`. linuxdeployqt is deliberately not used: its
glibc guard (≤ 2.35) predates this Qt's own 2.38 floor, so the Qt
runtime parts are copied explicitly from the distro prefix (the set is
in build.sh).

## Lint (clang-tidy)

Every commit must be checked with clang-tidy when it is available:

```
scripts/clang-tidy.sh <changed files>
```

With no arguments it checks all project sources and tests. The script wraps
`clang-tidy -p build` against a copy of the compile database (generated by the
build, see `CMAKE_EXPORT_COMPILE_COMMANDS` in CMakeLists.txt) with the GCC-only
`-mno-direct-extern-access` flag stripped — the distro's Qt6 CMake package adds
it for GCC builds, but the clang driver does not know it.

Configuration lives in `.clang-tidy` (production code) and `tests/.clang-tidy`
(relaxed variant; clang-tidy uses the closest `.clang-tidy` next to each source
file — each plugin's `tests/` carries the same relaxed variant). Checks are
enabled by family so checks added by newer clang-tidy releases are picked up
automatically; the exclusions in the files mark checks that fight Qt conventions
(QObject ownership, slots, enums) — keep the relaxed variants in sync.

## Command line

```
doob [--play] [--new] [--name <name>] [sources...]
```

The positional `sources` (files, playlist files, URLs) are imported on start,
and a second `doob` invocation forwards its command line to the running
instance and exits — the OS "play with doob" / "append to playlist"
context-menu use. `--help` / `--version` come from the
`QCommandLineParser` (the version is the project's, `DOOB_VERSION` define).

**Source resolution** (`CliImport::sourceFromArgument`, cliimport.{h,cpp}):
a scheme-bearing argument is a URL as pasted (a provider's, a stream's, a
`file:`); an existing path (absolute, or relative to the current directory)
is a file; anything else goes through `QUrl::fromUserInput` (the host-like
forms, which assume http).

**Routing** (`CliImport::import`): the sources go through the same import
paths the UI's adds use —
- a **playlist file** (a local file with an m3u/m3u8/pls extension) each
  becomes its own playlist via `PlaylistManager::importPlaylistFile` (named
  after the file, marked imported, its entries imported);
- the rest (**media**) go into the **current playlist** (like a drop), or
  into a fresh one with `--new` (named with `--name <name>`, the default
  "Playlist" without it — this Qt's parser has no optional option value,
  so a valued `--new` would eat the first source as the name).
- `--play` starts the playback on the **first imported track as soon as its
  row lands** (a one-shot `playlistChanged` watch, connected before the
  imports start — the rows can land synchronously for sources that need no
  read). The default leaves the playback alone: an append must not
  interrupt what is playing. With media sources that is the first media row
  of the media's target; with only playlist files, the first entry of the
  first imported file.

The manager's imports are **serialized** (one at a time), so the jobs of one
invocation run in the request's order, each chained on the previous one's
`importFinished` — the chain connections are one-shot (a synchronous finish
re-enters, and a stale connection would re-run the job forever), and a job
that starts no import (an unparseable file, no usable source) advances at
once. A second `import()` while one is running is refused (qWarning), like
the manager's.

**Single instance** (appinstance.{h,cpp}): `AppInstance::acquire(request)`
takes the gate — when no doob is running it listens on a `QLocalServer`
named after the **data directory** (`doob-` + the flattened path, so a doob
with its own `DOOB_DATA_DIR` is a separate instance) and returns true; when
one is, it forwards the request (one line of JSON — the sources and the
play/new-playlist flags) over a `QLocalSocket` and returns false (the caller
exits in milliseconds). The primary decodes and emits `payloadReceived` —
main routes it through the same `CliImport` as its own command line. A stale
socket file of a crashed predecessor is removed by the listen; a failed
listen is not fatal (the app runs without the gate, a second invocation just
exits).

**The order in main.cpp**: the `QCommandLineParser` runs before any state is
loaded, and `acquire` right after — a forwarded invocation exits before the
database opens. The `CliImport` runs after the plugins (a source's provider
may claim it) and the window (the `--play` playback is visible), but
**before the first-run dialog** — it is modal, and the command line's sources
must not wait for a layout to be picked (the async imports finish when the
event loop turns, i.e. after the dialog is answered; a forwarded payload
arriving while it is open is delivered right after).

Tests: `tests/cliimport_test.cpp` (the routing: current/new targets, playlist
files, the play watch, the job chain, the serialization) and
`tests/appinstance_test.cpp` (the gate: the per-data-dir name, the forward,
the wire format — the two `AppInstance`s in one test process play primary
and secondary).

## Adding a new widget

Reference implementations: `currenttrackwidget.{h,cpp}` (stateless display
widget driven by playback signals) and `positionslider.{h,cpp}` (widget with
local state). Follow the checklist; it touches five files, no more.

1. **Create `foo.h` / `foo.cpp`** at the repo root (lowercase names).
   Subclass `BaseWidget`:

   ```cpp
   class FooWidget : public BaseWidget
   {
       Q_OBJECT
   public:
       inline static const QString id = "foo";
       inline static const QString title = "Foo";
       // The "Set widget..." dialog's group (a free-form string — the
       // core's are the `widgetTags` constants in basewidget.h; a widget
       // that names no tag is grouped as "other"):
       inline static const QString tag = widgetTags::playback;

       explicit FooWidget(QWidget *parent = nullptr);
       QString widgetId() const override { return id; }
       QString widgetTitle() const override { return title; }

       // Only when the widget has persistent state. The base defaults
       // persist the instance name ("name", the objectName — see the
       // per-instance styling paragraph in docs/persistence.md); an
       // override
       // must chain to the base (start from BaseWidget::storeWidget()
       // / call BaseWidget::restoreWidget(config)) so the name keeps
       // travelling with the widget:
       // WidgetConfiguration storeWidget() override;
       // void restoreWidget(WidgetConfiguration &config) override;
   };
   ```

2. **Constructor**: `BaseWidget`'s ctor installs a zero-margin QHBoxLayout on
   the widget. If you need a different layout, `delete layout();` first, then
   install your own with zero margins. Give every child that tests need to
   reach a stable `objectName` (tests look them up via
   `findChild<T>("name")`). Grab the singletons
   (`PlaybackManager::getInstance()`, `PlaylistManager::getInstance()`,
    `LibraryManager::getInstance()`) and
   connect their signals in the ctor — widgets observe state this way, there
   is no other observation mechanism. Then initialize the UI from the
   *current* singleton state (re-run a slot with the current values, like
   `PlaybackControlWidget::updateButtons()`): signals only fire for future
   changes, so a widget inserted while something is already playing would
   otherwise start blank. A non-composite (self-painted) widget always sets
    a non-zero minimum size — even just 1 px, never 0 unless it is explicitly
    designed to collapse — so a tight layout cannot shrink it into nothing
    (composite containers get their minimum from their children and layouts,
    this is the self-painted widget's own job: `TrackLabelWidget`'s is the
    border plus one character wide, one line of text high).

3. **Register in `layoutmanager.cpp`**, two places:
   - `#include "foo.h"`
   - a registration in `registerBuiltinWidgets()` (called once from the
     `LayoutManager` ctor, idempotent — a taken id is skipped):
     `registry->registerWidget(FooWidget::id, FooWidget::title,
     [](WidgetConfiguration &) { return new FooWidget; },
     FooWidget::tag);`
     The `WidgetRegistry` (widgetregistry.{h,cpp}) backs `widgetOptions()`
     (the "Set widget..." dialog and clipboard paste validation) and
     `createWidget()` (also the dispatch used when restoring a layout
      document),
     so a registered widget is picked up everywhere.

4. **CMakeLists.txt**: add `foo.h foo.cpp` to `PROJECT_SOURCES` and
   `tests/foo_test.cpp` to `TEST_SOURCES` (each test source automatically
   becomes a CTest case named after the file stem).

5. **Tests** — `tests/foo_test.cpp`, one `QTEST_MAIN` class plus the trailing
   `#include "foo_test.moc"`. Copy the structure of
   `tests/currenttrackwidget_test.cpp`:
   - a `FakePlayer : AudioPlayer` (Q_OBJECT) as a `m_fake{this}` member —
     tests must never create a real playback driver (the built-in
     `NullPlayer` plays nothing; the FFmpeg player is a plugin)
   - `init()`: `PlaylistManager::getInstance()->reset()`,
     `PlaybackManager::getInstance()->setPlayer(&m_fake)` + `stop()`,
     construct the widget, `show()`, find children by objectName
   - `cleanup()`: `delete m_widget;` then `m_pm->stop();` and
     `m_pl->reset();`
   - a `registeredInLayoutManager()` test:
     `LayoutManager::getInstance()->createWidget(FooWidget::id, cfg)` returns
     a non-null widget whose `widgetId()`/`widgetTitle()` match

Then build, `ctest --test-dir build --output-on-failure`, and
`scripts/clang-tidy.sh` on the changed files.

### Toolbar

A widget can carry a toolbar strip (a `QToolBar` placed at the top or
bottom of the widget's box layout). The machinery is generic in
`BaseWidget` (basewidget.{h,cpp}); a widget opts in by:

1. **Calling `createToolbar(visibleByDefault)`** in its constructor, after
   it has installed its own `QBoxLayout`, and adding `QToolButton`s
   (optionally with `QMenu`s) to the returned toolbar. Give children
   stable `objectName`s. `visibleByDefault` is the state of a freshly
   created widget; only states different from it are persisted. Reference:
   `librarywidget.cpp` (a visible-by-default toolbar with a `+` add-menu
   button (an "Add folder..." action the playlist widgets' menus don't
   have), a `-` remove button, a view-mode toggle group, a busy indicator
    shown while a library operation runs — objectName `busyIndicator` —
   and a search box, objectName `searchBox`).
2. **Calling `storeToolbar(config)` / `restoreToolbar(config)`** from
   `storeWidget()` / `restoreWidget()`. The state is a `"toolbar"` map with
   `"visible"` (bool) and `"position"` (`"top"`/`"bottom"`); it is written
   only when it differs from the default and applied only when present, so
   a stale layout document can't reintroduce a default state.

The base class owns everything else: `setToolbarVisible`/`setToolbarPosition`
(repositioning just reinserts the strip into the widget's box layout), the
edit-mode context-menu entries ("Show toolbar" and "Toolbar at top/bottom",
added by the base `widgetContextMenu()` when a toolbar exists — the position
pair sits in an exclusive `QActionGroup`, the same as every option menu
(`TabPosition::positionMenu` does the same), so Qt draws options as radio
buttons and unchecks the previous one on a choice, while the single toggle
stays a plain checkable action), and the
public read-only accessors `toolbar()`/`toolbarVisible()`/`toolbarPosition()`.
`widgetContextMenu()` always returns a menu: it starts with the "Style
this widget..." action every widget gets (see the per-instance styling
paragraph in docs/persistence.md) and appends the toolbar entries when a
toolbar
exists. A widget with its own `widgetContextMenu()` actions should start
from `BaseWidget::widgetContextMenu()` and add to it (see
`playbackcontrol.cpp`). Widgets without a toolbar are untouched:
`createToolbar` is never called and the store helpers are no-ops.

**The media widgets' toolbars** share two helpers: `playlisttoolbar.{h,cpp}`
creates the button set the playlist widgets get — a "+" add menu (an
"Add files..." and an "Add by URL..." action) and a "−"
remove-selection button, parented and named (`addButton`/`removeButton`,
`addFilesAction`/`addUrlAction`), plus the `audioFileChooserFilter()` the
chooser shows — and each widget wires the returned buttons to its own
slots: `currentplaylistwidget.cpp` feeds the current playlist,
`playlistswidget.cpp` the playlist of the **displayed tab** (the tab's
`playlistId` property, resolved when the action fires). Both mirror the
drag & drop paths: chosen files go through the same `flattenDropFiles`
+ `importSources` a file drop does, appended at the end. The wizard
itself is `urlwizard.{h,cpp}` — a QObject owned by the widget holding a
single-instance `UrlImportDialog` (a second trigger raises the open one;
`open(lines)` prefills only a freshly created wizard) and routing its
`sourcesConfirmed` to the widget's sink — the library widget uses it too.

## Invariants (the cross-cutting contracts)

These hold across components; the component-specific detail lives in
`docs/`.

- **Write-through, no save on quit.** Every completed mutation is
  persisted immediately — memory first, then the database in one
  transaction; a failed persist rolls the memory change back and the
  caller skips its signal, so RAM and the file never drift and a crash
  leaves a consistent database. All writes funnel through the store's
  `insert`/`remove`/`setInLibrary`/`updateItem` and the playlist
  manager's row primitives — never write a component's table directly
  from elsewhere. The `SettingsManager` is write-through the same way
  (atomic temp-file + rename); the session state in it is best-effort.
- **The item store is the id authority.** Every item — library or not —
  lives in exactly one place with exactly one id;
  `MediaItemStore::resolve(id)` is the one lookup, and a dangling id
  renders empty/invalid without dropping the row.
- **Prune at mutation, never on a timer.** An item that is not in the
  library, referenced by no playlist and is `kind == Local` is deleted
  in place when it loses its last reference; non-local rows are never
  pruned (the row may be the only copy of their metadata).
- **Playlists never empty, never dedup.** The manager always holds at
  least one playlist; a playlist holds **item ids, never item data**,
  and may repeat an item any number of times — no add path dedups, so
  row operations are row-based.
- **`playingItemChanged` fires on stop too** (with an invalid
  `MediaItem`) — connecting to it alone keeps a display in sync.
- **Operations are asynchronous and serialized.** The library's file
  operations and the playlist imports run one at a time — tag reads on
  the worker thread, provider fetches on the GUI thread (the worker
  never touches a provider); a second call while one runs is refused
  with a `qWarning`.
- **Arrangement travels with the layout, behaviour with the user.**
  Everything about how the UI is arranged (the window's size/position,
  each widget's own state, view columns, the active tab) lives in the
  layout document, **never** in the `SettingsManager`; user
  preferences, session state and dialog UI state are registered
  settings in `settings.json`.

## Gotchas

- This Qt build's dbus module does **not** re-emit an adaptor's
  property NOTIFY signals as `PropertiesChanged` (the wiring is absent
  from its dbus module — `Properties.Get`/`Set` work, but the bus
  carries only the raw NOTIFY as a plain signal on the interface):
  anything the clients watch through `PropertiesChanged` (an MPRIS
  tray widget) must have the signal sent by hand
  (`Mpris::emitPropertiesChanged` is the instance — the spec's
  `(interface, changed, unchanged)` signal from the object's path).
  The same build's `Properties.Set` dispatch matches the **exact**
  `ssv` signature: the value crosses as
  `msg << QVariant::fromValue(QDBusVariant(value))`, a plain value
  would cross as its own type and the call fails with "No such
  method".
- This Qt (6.11) `QColor` `operator==` is sensitive to the color's
  **internal representation**: a painted pixel (`QImage::pixelColor`),
  a palette color of some roles (e.g. `Mid`), and a `lighter()`/
  `darker()` result can all fail `==` against an otherwise identical
  `QColor` (same spec, same ARGB). In tests, compare pixels by
  `.rgb()` (or `.name()`), not with `==`.
- CMake 4 parses `install(TARGETS)` strictly: `EXPORT <set>` must come
  **before** any `DESTINATION` clause, or the command fails with
  `unknown argument "EXPORT"`.
- This distro's Qt `QMap` iterator dereferences to the **value**, not a
  pair: iterate with `for (auto it = map.cbegin(); it != map.cend(); ++it)`
  and use `it.key()` / `it.value()` (`entry.first` does not compile).
- In tests, build `MediaItem.source` with `QUrl::fromLocalFile(path)` — a
  plain `QUrl(path)` parses as a URL and `toLocalFile()` returns `""`.
- `PlaybackManager`/`PlaylistManager`/`LibraryManager`/`MediaItemStore`
  /`SettingsManager` are singletons shared across test functions; always
  reset them in init/cleanup (`LibraryManager::clear()`,
  `MediaItemStore::clear()`, `SettingsManager::reset()` — point it at a
  temp dir and `load()` first, the way
  `tests/settingsmanager_test.cpp` and `tests/configpage_test.cpp` do;
  the library's worker thread lives for the whole process). Test items
  that must resolve (via `MediaItemStore::resolve`, `itemAt()`, playback)
  have to be registered in the store first (library items are store items with
  the `in_library` flag). Note that `init()`/`cleanup()` run before/after
  **every** test function — not once per suite like `initTestCase()` — and
  `QTEST_MAIN` allows one test class per executable.
- This Qt (6.11) `QSet` is implemented on `QHash`: iteration order is
  **arbitrary** (hash order), not sorted — never rely on it for a stable
  order. `LibraryManager` keeps membership in a `QSet` but `ids()`/`items()`
  sort explicitly into ascending id order, and `MediaItemStore::ids()`
  sorts the same way.
- Serialization goes through `WidgetConfiguration`; store enums as
  `static_cast<int>(...)` and never compare against hard-coded enum values.
- A direct slot call (`worker->doWork()`) runs **on the calling thread** —
  `moveToThread` only affects signal/slot delivery, not direct calls. To run
  work on a worker thread, dispatch it with
  `QMetaObject::invokeMethod(worker, &Worker::doWork, Qt::QueuedConnection,
  args...)`. Corollary: a signal emitted on the receiver's thread (as from
  such a direct call) is delivered synchronously — before a test's
  `QSignalSpy::wait()` starts waiting, which then times out on a signal
  that was "already emitted".
- The QTRY*/QFAIL macros expand to a bare `return`: they cannot be used in
  helpers that return a value. Wait for async state by spinning the event
  loop instead: `while (busy() && waited < 10000) { QTest::qWait(25);
  waited += 25; }` — a plain `msleep` deadlocks, because queued signals
  only deliver while the event loop runs.
- `QToolBar` re-shows its children when the toolbar is shown or re-laid
  out, so a `hide()` in a constructor (before the parent is shown) does not
  stick; a toolbar child that must stay hidden while idle has to re-hide
  itself from `showEvent` (see the `BusyIndicator` in `librarywidget.cpp`).
- Iterating `doc.object().constBegin()` directly hands out
  `QJsonValueRef`s into a **temporary** `QJsonObject` destroyed at the end
  of the full expression — the loop body reads freed memory (and only
  crashes when the object is non-empty). Bind the object to a named local
  first.
- TagLib 2.x is property-based: `FileRef::properties()` maps ID3v2 frames,
  Vorbis comments and MP4 atoms onto canonical keys, but the comment field
  is `COMMENT` for ID3v2/MP4 and `DESCRIPTION` for Vorbis — accept both
  (see `trackmetadata.cpp`). The ffmpeg muxer also writes an
  `ENCODER`/`ENCODING` tag, so the "extra" tags of a generated test file
  are never empty. This distro's TagLib also has **flat** headers —
  include `<fileref.h>` / `<tstring.h>`, not `<taglib/file.h>` — and
  `FileRef::isNull()` (there is no `isValid()`).
- `QTest` mouse events offscreen are delivered **directly to the widget
  you name** — no `childAt` routing, no QPA path: target the actual child
  (a `QScrollArea` or its viewport won't forward), and a right-click never
  synthesizes a `QEvent::ContextMenu` (that happens in
  `QWidgetWindow::handleMouseEvent`, which QTest bypasses) — send a
  `QContextMenuEvent` explicitly when testing context-menu behavior.
- Synthetic drag & drop works offscreen, but only the right way:
  `QDragEnterEvent` to `view->viewport()` first (it must be **accepted** —
  that registers `QDragManager::currentTarget`), then the `QDropEvent` to
  the same viewport; a drop with no prior accepted enter is silently
  discarded, and the model must accept the action via
  `supportedDropActions()`. A *real* drag over the empty area additionally
  requires `flags(rootIndex())` to include `ItemIsDropEnabled` — the
  synthetic enter+drop path doesn't check that flag, so the test passes
  while the real drag fails (see `MediaListModel::flags`).
- `QTreeView` defaults that bite: the header's `sectionsMovable` is
  **off** — `MediaListView` enables it explicitly for column reordering,
  and also un-pins the first section: `QHeaderView` additionally forbids
  dragging the section with **logical** index 0 (Title — visual order is
  irrelevant, so this is *not* about the column that shows first) unless
  `setFirstSectionMovable(true)` is set;
  `dragDropOverwriteMode` is **on**, so a drop on a row arrives at the
  model as `row == -1, column == -1` with the row's cell index as parent
  (empty-area drops get an invalid parent; row-edge drops with overwrite
  off get the insert row and an invalid parent) — `MediaListModel`
  normalizes all of it to an insert index. Also: `rootIsDecorated` is
  **on** by default (branch column, indent, child-drop positions) — a
  flat list must turn it off together with `itemsExpandable` and
  `expandsOnDoubleClick` (the media view is a **flat tree**: the model has
  no rows below the root); and unlike QTableView, QTreeView has no
  `horizontalHeader()`/`verticalHeader()` (use `header()`), no grid, and
  no `selectRow()` (`MediaListView` provides one).
- `QAbstractItemView::setDragDropMode()` silently resets
  `dragEnabled`/`acceptDrops` (DropOnly ⇒ dragEnabled=false) — the
  playlist views use `enableDragAndDropping()` (DragDrop, set last) so
  rows can be dragged to reorder.
- Binding a default-constructed `QString` to a `QSqlQuery` binds SQL
  `NULL` even though `QVariant(str).isNull()` is false — it fails
  `NOT NULL` columns. Bind empty strings explicitly (`QStringLiteral("")`
  is non-null, `QString()` is null); the managers guard at the bind site
  (`Database::nonNull()`). Related: when reusing a prepared query across `exec()`
  calls, `bindValue(index, …)` replaces at that index — `addBindValue`
  would append.
- A live `QSqlQuery` that read a table's schema (`PRAGMA table_info(T)`)
  holds a read lock on it: `DROP TABLE T` on that same table fails with
  `database table is locked` while the query object is still alive (Qt
  keeps the prepared statement alive as long as the query object exists,
  even after the rows are consumed). Scope the schema-reading query before
  the DDL (`Database::tableColumns` does this for migration steps).
- This distro's QtSql has no `QSqlTransaction` (the class and header are
  absent from the build) — use `QSqlDatabase::transaction()` / `commit()`
  / `rollback()` directly (as the managers' `save()` and
  `Database::open` do).
- `qWarning` takes a C varargs format string: a `QString::arg`-style `%1`
  placeholder reads a non-existent vararg and segfaults in
  `QString::vasprintf`. Use `%d`/`%s` with `qPrintable(...)`.
- `QJsonValue` has no `qulonglong` ctor and no `toULongLong()` — go via
  `double` or `toVariant().toULongLong()`.
- Emitting signals in tests: this Qt (6.11) `QMetaObject::activate`
  exposes only the `void **argv` overloads —
  `std::array<void*, N> args = { nullptr, &arg1, … };
  QMetaObject::activate(obj, signalIndex, args.data());`. Invoking a slot
  by name with an argument: `QMetaObject::invokeMethod(obj, "slot",
  Q_ARG(Type, value))` (see the `doubleClicked` helpers in
  `tests/playlistswidget_test.cpp`).
- A synthetic `QMouseEvent` for tests: pass the clicked button in **both**
  the `button` and `buttons` args — handlers check `event->button()`,
  which reads the `button` arg only.
- `QTabBar` is only as wide as its tabs (`QTabWidget` does not stretch
  it) — the strip right of the tabs belongs to the `QTabWidget`, so the
  tab-bar event filter (middle-click close, double-click on empty space)
  is installed on **both**, with positions mapped via `mapFrom` (see
  `playlistswidget.cpp`).
- A test must **never link a plugin .so**: the plugin's Q_OBJECT
  metaobject symbols (`staticMetaObject`) live only in the plugin
  library, so a `qobject_cast<PluginClass*>` in the test is an undefined
  reference at link time. Reach the plugin's state through observables —
  the core registries (what it registered) and a record it writes to
  the `SettingsManager` (see `tests/pluginmanager_test.cpp` and the fake
  plugin's `api` record under `fakeplugin.api`).
- `QPluginLoader`: `unload()`/deleting the loader **deletes a
  parent-less plugin instance** (and everything it parented) — which is
  why a plugin's `shutdown()` must unregister its core-side entries
  first, and why a plugin must guard `shutdown()` for an
  `initialize()` that bailed (a null api). Related: `metaData()`
  returns a `QJsonObject` in Qt6 (a `QVariantMap` in Qt5), and a
  `Q_PLUGIN_METADATA(... FILE "...")` JSON must exist when moc runs.
- `QTemporaryDir` has **no path setter** — the fixed path goes in the
  constructor (`QTemporaryDir dir{"/tmp/.../fixed"}`).

## Rules

- Always add or extend automated tests in `tests/` when adding or changing behavior.
- New widgets: follow the "Adding a new widget" checklist above.
- New dialogs: plug them into the `UiState` helper for their size,
  position and internal state (the `dialogs.*` setting) — see the dialog
  UI state paragraph in docs/persistence.md.
- Plugins: a plugin's `initialize()` registers into the extension
  points, its `shutdown()` unregisters them (see docs/plugins.md); test
  plugin
  behavior through the fake plugin (`tests/plugins/`), never by linking
  the plugin into a test.
- Ownership: default to Qt parent-child for QObjects and value semantics for
  data. Reach for smart pointers only where the parent relation doesn't cover
  the lifetime — `std::unique_ptr` for a solely owned non-QObject,
  `QSharedPointer` for a shared non-QObject payload. Never wrap a QObject that
  has a parent in a smart pointer (double deletion), and never keep a pointer
  into a `QList`/`QHash` of values (reallocation invalidates it) — address
  items by a stable id and resolve against the owning container.
- DRY, with a trigger (the rule fires at a moment, not as a vibe):
  - **The third occurrence is the threshold.** Two similar blocks is
    tolerable duplication (the abstraction may be premature); the third
    must be extracted — it proves the shape is stable. Before writing a
    function that is structurally the same as an existing one (same steps,
    different data or parent), search for the existing one and extract a
    shared helper.
  - **New widgets/views/dialogs:** the checklist says to copy a reference
    implementation's structure — copy the *structure*, share the
    *plumbing*. The shared helpers exist (`chooseAudioFiles` and friends in
    `playlisttoolbar`, `dialogplumbing.h`, `vizwidget.h`, `metadatable.h`,
    `rowclipboard`, the named-file-store core in `entrystore.h`) — search
    for them before writing a second similar block.
  - **No parallel mechanisms:** when an extension point exists (widget
    registry, `SettingsManager`, settings topics, the source/player/DSP
    registries, the `DoobApi` facade), extend it — never a second path
    around it.
  - **State lives with its owner:** a value a singleton already holds is
    observed through its signals, never copied into a widget's or manager's
    own field and kept in sync.
  - **Self-check before the task is done:** grep for the pattern you just
    wrote; if an existing one matches, extract. When extracting, prefer a
    small helper or free function over a base class (the dedup chose
    helpers — `chooseAudioFiles`, `dialogplumbing.h` — over hierarchies).
- SOLID, mapped to this codebase (the generic definitions don't apply as
  written):
  - SRP: the "and" test — a unit whose description needs an "and" is two
    units.
  - DIP: depend on the singletons' signals, the registries and the
    `DoobApi` facade; never reach into another component's internals — when
    a seam is needed, a protected virtual (the test-seam convention).
  - OCP: new behaviour lands in an extension point, not a branch in core
    code (no `if (widgetId == "foo")` walks — dispatch through the
    registry).
  - ISP: optional capabilities follow the `AudioPlayer` pattern — a virtual
    with a default implementation (`supportsVolume()`-style), not a new
    interface a driver must implement whole.
  - LSP: does not apply here — Qt's ownership model (parent-child, value
    semantics) already fixes substitution; don't refactor for it.
